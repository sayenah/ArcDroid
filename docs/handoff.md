## Slice 14 work order — boot-outcome fallback: a self-booting disc whose boot ends at the RISC OS command prompt is launched through discovery (broken-launch class G7 and its family)
**Objective.** Some discs carry a boot option and a root `!Boot` that, under RISC OS 3, ends at the Supervisor `*` prompt instead of starting anything: G7's Arthur-only boot programs (119, 125, 197 — the program checks the OS version string, raises an error and tells the user to launch the application by hand), and other prompt-enders in the same family (47, 48: the boot's setup program runs out of RMA; 24, 99, 114, 143, 185: JFDs whose own boot stalls natively; 68, 69 natively without a package; 32, 38 until Slice 13 lands). The machine waits for a command for ever. Fix the class generically (PRD P-4, D-090): ArcDroid observes, at the ARM SWI level, that the disc's own boot has ended with RISC OS waiting at its command line, and then does what the user would do — it applies its ordinary launch discovery to the same disc: the unique application is launched through the existing drive-1 helper, several verified applications open the launch chooser, none → nothing more than a log line and one notice. No content inspection of boot programs, no per-title data, no cache, no option.

**Scope.**
C-1 **Boot observer (engine).** One marked call at the entry of `opSWI` (`engine/arculator/src/arm.c`, `/* ArcDroid modifications */`, no policy in the upstream file) hands each executed SWI instruction (24-bit number with the X bit cleared separately, R0–R3, the calling instruction's address corrected for the engine's PC representation, processor mode) to a project-owned observer in the engine layer (`engine/`, ArcDroid file). The observer is a bounded state machine: no allocation, no guest-memory reads, no logging, no register mutation, no adapter callbacks in the hook; it is unit-testable in isolation. Lifetime: armed by the adapter through one dedicated engine call after a successful `arc_engine_start` of an eligible session (C-2); cleared on `arc_engine_stop`, on a failed start, on `arc_engine_reset` (the adapter re-arms explicitly if it wants); never armed twice for one attempt. Rule, all in **emulated time** (the engine's guest clock), with SWI events recorded with their guest timestamps during the frame and the state **advanced unconditionally at every completed engine frame** (so a read followed by no further SWIs still confirms) and finalised only after every event of that frame has been considered: (a) the **horizon** is 40 s from arming; when it expires without a confirmed prompt the observer disarms (`expired`); confirmation falling exactly on the horizon counts as expiry; (b) `Wimp_Initialise` (&400C0, X or not) → disarmed for the attempt (`disabled`, desktop started); (c) `OS_ReadLine` (&0E, X or not) with R0 < &8000 **and** the calling instruction inside the mapped firmware ROM → a **pending command-line wait** starts at that instant (another such read restarts it); (d) `OS_CLI` (5, X or not) → cancels the pending wait (a command was executed) without disarming — a later qualifying read may start again; (e) a pending wait that lasts **2 s** of emulated time with no cancellation, inside the horizon → the observer **latches `prompt`** and disarms; a cancelling event in the same frame as the confirmation wins. The API separates read cancellation (still armed) from the adapter's permanent cancellation (`cancelled`, C-2). Nothing else is inspected: no ROM addresses beyond "in ROM", no strings, no screen, no host timers, no keyboard state. `arc_engine_boot_watch_state()` (armed/disabled/expired/cancelled/prompt) is read by the adapter after `arc_engine_run_frame` returns; a guest reset-vector branch does not restart the horizon. A test hook may feed synthetic observations to the state machine, but the harness evidence of C-4 comes from executed SWIs.
C-2 **Recovery policy (adapter).** Eligible session: `Launch: Auto`, image 1, launch preparation ended in `DISC_BOOTS_ITSELF`, supported OS class (`arc_launch_os_supported`), native or no-package JFD path, no helper, no ADFFS or install plan, no explicit pick, no chooser (the D-084 table is neither consulted anew nor changed). The adapter arms the observer after the machine is constructed and **cancels it permanently on meaningful frontend input** (keyboard/OSK key, pad button, stick beyond the existing deadzone, mouse movement/button, touch; controls held at construction count; polling, neutral samples and analog drift do not), on media manipulation (eject/insert/index change) and on an engine fault; it is gone after the recovery. Discovery at preparation is unchanged (same `reason`, fingerprints, helper bytes). When `prompt` is latched (seen after `arc_engine_run_frame` returns, machine held at a completed frame boundary): **(1) rediscover** the current guest-visible media (effective sectors, including boot-time raw/JFD writes) with the existing discovery; **(2) decide** from that fresh discovery: **automatic** only when the scan is complete, exactly one non-resource candidate is an application, no candidate is unknown, no other known application exists (launchable or not) and that application is launchable; otherwise **chooser** whenever at least one verified launchable target exists (incompleteness/unknown status supplied to the chooser explicitly, without rewriting the original discovery reason); otherwise **none**. Automatic or a chooser pick: **(3) publish** the helper for the target resolved by its validated path (`arc_launch_helper_publish`) **before any teardown**; on failure resume the prompt with recovery disabled and one actionable error, exposing no partially updated launch plan; **(4) persist** — synchronise the live CMOS, copy the normalised record into the private prepared seed and attempt persistence while the session still counts as running (the in-memory seed is kept even if the write fails); **(5) commit** — stop the engine, re-prepare the media through the existing store path (committed writes preserved), validate that the discovery still matches the published target (else terminal failure), construct through the normal helper path (helper as boot drive; content identity, machine, firmware, write mode unchanged), AV transition per D-048; a failure after the commit point reports one error and does not retry. **Chooser:** step (4) runs **before** the chooser is entered; the live machine is held without stepping while the existing chooser (renderer, candidate list, controls, record validation, release gate, D-048 AV rules) is shown in a post-boot mode whose negative row is "Continue without launching" (resumes the prompt with recovery disabled); a pick runs (3) then (5); a valid remembered `.choice` for the disc is honoured **after detection** without showing the chooser unless `Launch chooser` = ask; a remembered negative choice continues; picks are recorded exactly as today; reset/unload while the held-machine chooser is open persist from the prepared seed and behave as for a running session; no `.choice` ever suppresses the self-boot at load. **None:** one INFO line and one non-blocking notice; the guest keeps running at the prompt. **One recovery per deliberate boot attempt** (content load or frontend `retro_reset`); the replacement machine never re-arms; `retro_reset` starts a fresh attempt under the current options (a valid C-6 record skips the failed boot). No manufactured `.choice`, no option; the only durable state is C-6's boot-observation record.
C-3 **Diagnostics.** `Launch:` keeps every existing field (`discovery-reason=disc boots itself` untouched) and adds `phase=initial|recovery`, `boot-watch=armed|disabled|expired|cancelled|prompt` and, on a recovery line, `recovery=helper|chooser|none|failed` with the decision/target escaped as today. One INFO line per detected prompt with the emulated time and the chosen action. Frontend: nothing on a successful automatic recovery (an optional brief transition message is allowed), the chooser explains itself, one notice with no target ("Disc startup stopped. No application could be selected automatically."), one actionable error on publication or reconstruction failure. Nothing per-title, no detector mechanics, no error-string extraction.

C-6 **Remembered boot observation (Founder S38, D-093; Astra stage 3).** After a confirmed prompt whose recovery published a helper (automatic or a pick) or offered the chooser, the adapter writes a **boot-observation record** `<save>/arcdroid/launch/<content_id>.boot`: a single **"observed terminal prompt" marker** with validity stamps and no target, no helper/chooser discriminator and no title text — {record version; **cache-compatibility revision** (a constant bumped when launch or engine behaviour relevant to the observation changes); resolved firmware digest; machine, CPU and memory; digest of the **effective native media presented to the observed boot** (validated base/store digests of every image of the set plus set membership and order, captured **before** the observed boot); digest of the **normalised starting CMOS payload** of the observed boot; boot-affecting options as resolved (`JFD Boot`, `Disk Writes`, install-saves mode)}; grammar: fixed field order and count, fixed digest lengths, maximum size, no duplicates or trailing bytes; publication through the existing temporary/previous replacement discipline; a write failure never fails the launch and never touches `.choice`/`.bind`; nothing is written from a notice-only outcome or when the effective media changed during the failed attempt. **Consultation** happens only after normal routing selected an eligible native image-1 session with `Launch: Auto` whose fresh discovery says `DISC_BOOTS_ITSELF` (never on ADFFS/install paths, never forcing a route, never altering D-084 precedence; `Launch: Off` and explicit `Application N` neither consult nor create records and keep the unchanged `.bind` guard): a record whose stamps all match the current resolved values is a **hit** — the disc is prepared **as if it did not boot itself**: ordinary discovery applies with today's precedence (`ask` / a valid user `.choice` incl. a remembered negative → then fresh automatic selection → chooser), the helper or the pre-boot chooser boots directly and the observer is not armed; a **negative choice on a hit runs the disc normally with recovery disabled for that attempt**. Any mismatch, or a malformed/truncated/oversized/unsupported record, is a miss: the record is ignored (removed when malformed, removal failure not blocking) and the disc is observed again. A helper publication or construction failure on a hit deletes the record (suppressed in memory even if deletion fails; one error; no repeated reconstruction in the attempt) and the next load re-observes. `retro_reset` performs the same validation as a new preparation (a valid record skips the failed boot; this supersedes "every reset repeats observation"). Precedence overall: **Off/explicit → routing → valid boot observation → `ask`/valid `.choice` → fresh automatic selection or chooser**; the record never outranks a user choice. The record is run-time derived state under D-093: never shipped, keyed by content identity plus resolved environment, re-derivable and self-invalidating; it records that the prompt was observed, not that the application works.
C-7 **First-boot CMOS default (D-095).** The fresh CMOS payload ArcDroid seeds for RISC OS 3.10/3.11/3.19 sessions when no persisted record exists (both IO classes) carries logical byte 195 with bit 2 clear — the value the firmware itself writes on first boot — so a title's first launch starts from the state its later launches start from. Applied in core where the default payload is produced; the upstream dumps under `engine/arculator/cmos/` are unchanged; RISC OS 3.00, RISC OS 2, Arthur and existing persisted records are untouched; the checksum is recomputed at construction as today.
