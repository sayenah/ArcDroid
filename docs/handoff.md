## Open question: Elite pad play (blocks the "plays from the pad" claim)
Facts established on the Odin3 with `f3139b8`:
1. The Odin3 built-in pad reaches the core as **two RetroArch devices**: sticks and shoulders on port 1, d-pad and face buttons on port 2. Evidence: before R-116 a physical Start press arrived in the KART trace as Escape (the generic port-2 Start). R-116 mirrors single-port profiles onto port 2.
2. With R-116, the Founder's physical presses **do reach the guest as the Elite keys**: the KART trace of the last test contains F1 ×10, `S`, `X`, `,`, `.`, `/`, Space, plus mouse buttons — every key down followed by its key up.
3. The Founder reports the game does **not** respond to d-pad/A/B/Start, while the right stick (mouse) flies the ship and R1/L1/L2 (mouse Select/Adjust/Menu) fire/accelerate/decelerate — Elite's mouse controls work through the existing pointer path (D-026).
4. Earlier, a held physical-keyboard `S` over adb (`input keyevent --longpress`) made the ship dive, so Elite does act on keyboard keys delivered through the same FIFO/KART path.
5. The KART log has no timestamps: consecutive down/up packets do not indicate hold length, so the log cannot distinguish a 10 ms tap from a 3 s hold. Fable's earlier "1-packet hold" inference was wrong and has been retracted.
Hypotheses, untested: (a) the Founder tapped rather than held, and Elite's per-frame key polling misses short taps (a held d-pad test was requested but not yet run); (b) continuous small pointer motion from the right stick (drift, `7E,00` packets) keeps Elite in mouse mode so keyboard flight keys are ignored; (c) something in the adapter shortens pad-held keys on the device only (nothing found in `arc_poll_inputs`, `arc_input_pad_key_sets`, `arc_input_source_key`, `arc_poll_keyboard_snapshot`, `arc_poll_osk_controls` by reading; the harness holds pad keys across frames with keyboard polling enabled at `tests/libretro_harness.c:1585-1703`).
Next steps: Founder holds d-pad left 3 s, B 3 s, Start 1 s with the stick untouched; if holds work, (a) is confirmed and the profile is verified. If not, add guest-time timestamps to the device evidence (a test-build KART trace with `guest_us` exists under `ARCDROID_TEST_FAULTS`; a device build of the test core is possible but must never ship) or reproduce on the host with `--osk-script`-style scripted pad holds against the private ROM and the Elite disc.

## Device/tooling facts learned this session (keep)
- Synthetic input over adb: `input keyboard text/keyevent` reaches the core's keyboard callback **except** keys RetroArch binds to the RetroPad by default (`z x a s q w e r`, arrows, Return, Right Shift): those are dropped when game focus is off. `input keyevent KEYCODE_BUTTON_A/B/THUMBL/START` reach the core as RetroPad B/A/L3/Start; `KEYCODE_DPAD_*` and `BUTTON_L1/L2` do not arrive as pad input. Synthetic pad presses become unreliable within a session after a few uses (observed: a later synthetic L3 or A producing no effect); a fresh `am force-stop` + `am start` restores them. The physical stick click did not arrive as L3 for the Founder (RetroArch port binding to check: Settings → Input → Port 1/2 Controls).
- Launching Elite by hand (the Slice 2b discovery marks the disc unreadable because of the non-ASCII `!élite` name — follow-up): at the RISC OS desktop, F12, `filer_boot adfs::0.$.!system`, Return, `filer_run adfs::0.$.!#lite`, Return, empty Return (closes the line so the queued desktop commands run); the Jameson icon appears bottom-right; move the pointer by trackpad swipe (≈1.5 screen px per swipe px) and tap to click it; the manual-word check follows (Fable reads the word from the manual PDF page image: printed page N is PDF page ⌈(N+1)/2⌉+3 roughly — pp. 18–19 = PDF 13, 24–25 = PDF 16); type it via the OSK by touch (full-layout key cells: rows y≈655/730/805/875/950/1025; TAB row Q…P x≈320…940; LCT row A…L x≈340…870, RET 1095; LSH row Z…M x≈320…735) or via `input keyboard text` when no letter is RetroPad-bound; Space on the title → commander screen; F1/Start launches.
- Disk control over UDP 55355: the tray is a toggle and `DISK_NEXT` is silently ignored while closed; RetroArch writes `<playlist>.ldci` on quit and restores that index at the next launch. The earlier "`.ldci` regression" was retracted (operator phase error, Opus reproduced correct behaviour).
- Elite's demo/practice and Saloon Cars Deluxe's demo ignore keys; Saloon's menu is mouse-driven.
