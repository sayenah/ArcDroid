### Scope
1. **Drive roles for ADFFS sessions.** Drive 0 = support disc (package subset, stage 1, launcher), boot drive 0 with two floppies configured. Drive 1 = a carrier holding exactly one JFD, the verbatim bytes of the disc currently served, as `$.Disc<n>`, `<n>` = the disc's 1-based position in the set (D-056 order). Stage 1 copies from `ADFS::0`; the launcher mounts `ADFS::1.$.Disc1`, dismounts both drives, then `ADFBootFloppy`. Single-JFD sessions use the same path (one launcher text).
2. **Disc change = place, then press — one in-flight swap transaction.** A frontend insert of index i under ADFFS: (a) synchronous checks — session running and ready (§4), no swap pending, index valid, keys neutral (no user-held modifier or F-key in the effective input state); any failure returns false with an OSD naming the reason; (b) build carrier i+1 completely, then replace the drive-1 medium with the disc-change interrupt; if the install fails, restore the previous carrier and return false; (c) deliver Ctrl-Shift-F<i+1> as a genuine chord through the existing phased activation machinery from a dedicated core source (not shown in the OSK, never interleaved with user modifiers; the same activation cannot be used by the OSK meanwhile); (d) the transaction stays pending until the completion signal or the bounded wait (§4). **Every insert sends the chord** (no skip for the same disc: the core cannot know what ADFFS serves). A user-pressed Ctrl-Shift-F1…F9 (keyboard or OSK) during an ADFFS multi-disc session is intercepted (press and release suppressed from the guest, autorepeat ignored, F<n> above the set size logged and dropped): the request is armed, the carrier is placed and the chord sent only once the user's keys are neutral (bounded wait; timeout logs `dropped`, nothing placed), then the frontend index is updated.
3. **Eligibility** (before launch discovery, as D-050): every prepared image is a JFD; 1 ≤ count ≤ 9; image 1's header `disc_number` ≤ 1; every member's raw size ≤ `ARC_ADFFS_CARRIER_CAPACITY`; package, OS and option conditions unchanged. New native reasons: `mixed-formats`, `too-many-discs`, `too-large` (log names the disc position). Applies to zip sets, folder sets and m3u alike. Raw bytes of every eligible member are retained at load (bounded: ≤ 9 × `ARC_ADFFS_CARRIER_CAPACITY`; zip members through `core/zip.c` with the D-054 limits; file-backed members read once and digest-checked against the prepared identity), so an insert never touches the archive or the file system. A failed drive-1 insert leaves the index and the guest untouched, shows the existing error OSD, sends no chord.
4. **Disk control under ADFFS:** count = set size; `get_image_index` = the frontend-selected index; labels/paths unchanged; `set_eject(true)` accepted while no swap is pending (state only — **eject is logical under ADFFS**: the old disc stays readable by the game until ADFFS loads the next; documented, and put to the Founder) and refused while pending; `set_index` while ejected; `set_eject(false)` = the transaction of §2; `replace`/`add` refused; every load boots disc 1 (D-044/D-045). **Progress-only contract (no completion claim):** the engine exposes a shipping per-drive FDC activity generation (both controllers); the log records `ADFFS disc: index=<i> name=Disc<n> chord=ctrl-shift-f<n> source=<frontend|keyboard|osk> phase=requested` at the chord, `phase=read-observed` when drive-1 reads of the new carrier are seen, `phase=not-read` after a bounded wait; the core tracks `last_read_observed_index` and never claims which disc ADFFS serves; OSD `Disc <n>: ADFFS reading` / `Disc <n>: ADFFS did not read the disc` (never "inserted"). **Readiness/quiescence:** a request is accepted only after at least one drive-1 read since boot and no drive-1 FDC command within the last K frames (K a named constant, chosen from Checkpoint A evidence — the same rule protects a carrier while guest work may be outstanding); otherwise refused with OSD `ADFFS busy — try again`. A timed-out swap clears pending, keeps the selected index and the placed carrier, logs `not-read`; the next request is a fresh transaction. **Reset** revalidates the whole set, rebuilds support + carrier 1, resets selected/active to 0 and re-boots; it never switches to native because a later disc was selected; reset and unload cancel any pending chord and release every core-held key. For sets of 2+ discs the launcher emits `ADFReserveMemory <max decoded size across the set, KB>` before `ADFBootFloppy` (Checkpoint A verifies; removed if it breaks the real package).
5. **Rider R-1 — no per-game `.srm` (D-011 amendment).** `retro_get_memory_size(RETRO_MEMORY_SAVE_RAM)` returns 0 and `data` NULL; the D-019 write-through file remains the only CMOS record; harness SAVE_RAM assertions become write-through-file assertions of the same intent; `docs/zip.md` gains the RetroArch scan note ("Scan Inside Archives" off = one entry per zip; on = one entry per member, all booting image 1) and states that old `.srm` files are inert and may be deleted.
6. **Rider R-2 — CI driver hardening (test-only).** `tools/test-retroarch-windows.ps1`: bounded retry of the in-session reload step (`:327`) and of the two screenshot `Move-Item` sites (`:620`, `:936`) with the attempt count in the log; no behaviour change when the first attempt succeeds.
7. **Rider R-3 — zip member mode robustness (Run 2).** `arc_zip_content_member`: a Unix-origin entry whose mode has zero file-type bits (`mode & 0170000 == 0`) is a regular file; entries typed as directory/symlink/device stay rejected; a `zip-content` test with a Python-style `0600` member and a negative for a symlink-typed member.

- Never: write host storage or the package; log package bytes or library names; change identity; put any JASPP byte in fixtures (synthetic package only).
