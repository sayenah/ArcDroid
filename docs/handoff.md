## Objective and governing requirement
A boot-option-0 FileCore disc that carries a launchable RISC OS application reaches that application without desktop interaction (PRD §2, P-3, FR-24), through the platform's own desktop boot-file path, with a RetroArch-native per-title override (FR-50, FR-22) and a fallback to the desktop (FR-26). No title-specific patching (FR-25). User media are never modified (D-014). Governing: PRD §11, §16, §23; protocol §8–§13; D-012, D-013, D-014, D-019, D-021, D-025, D-028, D-029, D-030, D-031.

## Scope
1. **Discovery** (pure, bounded, in `core/`): read the effective drive-0 bytes (staged shadow for raw images; for JFD a geometry-aware accessor over the validated sector table: track index = cylinder×2+side, 5×1024-byte sectors per track-side for D/E and 16×256-byte for L, density from the descriptor; a required sector that is missing, duplicated or flagged with a bad ID/data CRC makes the disc unreadable for discovery) and produce a decision. Boot option: byte 509 (L/D) or disc-record byte 7 (E). Root: L at &200 (old 47-entry directory, 1280 bytes, `Hugo`, attributes in name top bits), D at &400 (new 77-entry directory, 2048 bytes, attribute byte +25), E via the disc-record root indirect address resolved through the single-zone new map (fragment id + sector offset; fragmented objects resolved from the map, otherwise unreadable). New-format directories accept either `Hugo` or `Nick`; validate start/end markers, sequence bytes, bounds and extents. Unreadable → no automation, media still loads. Candidates = every root directory named `!` + 1–9 characters of `A-Z a-z 0-9 _ - +`, excluding `!Boot`, `!System`, `!Fonts`, `!Scrap`, in directory order (the whole root is scanned; only the option ordinals stop at 8). Each candidate is inspected: **application** = contains a non-directory object named `!Run` (case-insensitive; old-map addresses ×256; new-map via fragment resolution); **inspection failure** (unreadable directory) is distinct from "no `!Run`" and makes the automatic decision `none: inspection incomplete` — never a uniqueness claim. Selection: exactly one application → target; several → the unique application whose normalised name (`!` stripped, lowercase, `[a-z0-9]`) equals the normalised disc name, or equals it after stripping trailing digits from the disc name; otherwise no target. Directory order, size and any other heuristic never decide. The disc-name rule is an overridable heuristic over a complete application list, not proof of identity. Non-zero boot option → no automation (disc boots itself) unless an explicit Application override is set. JFD flags/sequence/obey: diagnostics only.
2. **Launch disc** (pure builder in `core/`): 640 KiB L-format image, old map (checksums, boot option 2, disc name `ArcDroid`), old root directory with `!Boot` (Obey &FEB: `| ArcDroid launch disc` / `Desktop -File ADFS::1.$.ArcLaunch`) and `ArcLaunch` (Desktop &FEA: `| ArcDroid desktop boot file` / `Dir <disc>.$` / `URD <disc>.$` / `Filer_Run <disc>.$.<target>` where `<disc>` is `ADFS::<discname>` when the trimmed disc name is 1–10 characters of `A-Z a-z 0-9 _ - +`, otherwise `ADFS::0`; a named reference binds the dispatch to the planned disc so an early swap yields ADFS's insert-disc prompt instead of silently launching another disc), files placed with the sequential-side sector mapping; bytes are a deterministic function of the target. Published to `<save>/arcdroid/launch/<content-id>.adl` by temp+flush+close+rename; an existing file is reused only if its bytes match; failure → no automation.
3. **Engine two-drive path**: helper media retained separately from drive-0 media; mounted in drive 1 always write-protected (per-drive write policy replaces the global raw flag; drive 0 behaviour unchanged); re-mounted on reset; never exposed through libretro disk control, content count, identity or paths; JFD stays drive 0; eject/insert/replace affect drive 0 only.
4. **CMOS overlay** (D-031): configured drive and floppy count are launch-owned: machine image gets drive 1 / floppies 2 when a helper is mounted, drive 0 / floppies 1 otherwise; every payload synchronisation (SAVE_RAM and save file) normalises those fields back to drive 0 / floppies 1; other guest changes persist as today.
5. **Core option** `arcdroid_launch` ("Launch"): `auto` (default) | `off` (native boot, no helper, no overlay) | `app1`…`app8` (candidate index; beyond the list → warning + no automation; the selected candidate must be an application). Applies at load and reset. An explicit Application choice also overrides a non-zero boot option (logged: the disc's own `!Boot` is skipped because the helper is the boot drive). **Binding**: when an `appN` choice is applied, the adapter writes `<save>/arcdroid/launch/<content-id>.bind` (text: option value, resolved target name, candidate-list fingerprint); on later applies with the same option value, a resolved target that differs from the bound one → warning OSD, no helper (the user re-selects, which rewrites the binding). `auto` and `off` ignore and do not write bindings.
6. **Gating and reporting**: automation only for OS classes RISC OS 3.00/3.10/3.11/3.19; Arthur/RISC OS 2 unchanged. One INFO line per decision: boot option, disc name, numbered candidates, applications, decision, reason, helper path. One OSD message only when candidates exist but no target was chosen, listing the numbered candidates so the handheld user can pick without the log (e.g. "No unique application: 1 !Install 2 !RunToRead 3 !SALOON — set Launch to Application N"; truncated to fit), or when a binding or explicit choice is refused (reason named). Discovery runs on the image in drive 0 at each machine start (load honouring `.ldci`, and reset); ejected/empty → no helper.
7. Fix `core/launch.c:111` (byte 510 is the free-space end pointer; byte 509 is the boot option, exposed in `ArcMediaInfo` with the disc name). Allowed incidental fix: `engine/arculator/src/arm.c:661` signed-shift cast.

### Non-goals
Arthur/RISC OS 2 automation; executing JFD obey files or acting on JFD flags; HostFS; profile records/database (deferred until a real disc demonstrates unresolved ambiguity); dynamic content-specific option values; keystroke injection; save states; new media formats; on-screen keyboard; PRD changes.

## Architectural constraints and affected interfaces
- `core/arcdroid_core.h`, `core/launch.c` (+ new discovery/builder units): `arc_media_inspect` gains boot option and disc name; new pure APIs for discovery and launch-disc generation; `ArcLaunchPlan` gains launch fields; `arc_cmos_machine_image` gains the helper flag and a payload-normalisation helper.
- `engine/arcdroid_engine.h/.c`, `engine/arculator/src/disc_adf.c`: helper media descriptor for drive 1, per-drive write policy, reset re-mount.
- `libretro/arcdroid_libretro.c`: option, decision at load/reset, helper publication, logging/OSD, payload normalisation on sync. `arcdroid_libretro.info` unchanged.
- `tests/generate_fixtures.py`, `tests/core_tests.c`, `tests/libretro_harness.c`, `tools/test-retroarch-windows.ps1`, `.github/workflows/ci.yml` as needed. No new permanent docs.
- Early swap policy: dispatch is disc-bound by name where possible; a swap before `Filer_Run` therefore surfaces ADFS's insert prompt or a Filer error, both recoverable from the desktop; the adapter never retries or re-dispatches after a swap.
- Security: fixed command templates; names and disc names outside the grammar disable automation; no JFD obey text, labels or host paths in generated files; helper files digest-named under the owned `launch/` directory; never delete game shadows as helper cleanup; handles closed before replace/remove (Windows); incomplete helper files recovered after Android process death.

## Acceptance criteria
- AC-1 Engine mounts a raw L-format helper in drive 1 write-protected while drive 0 holds raw or JFD media; the WD1772 path can select drive 1 and read its map sector; drive-0 write policy is unchanged; reset re-mounts both; eject/insert/replace touch drive 0 only.
- AC-2 CMOS overlay: machine image carries drive 1 / floppies 2 with a helper and drive 0 / floppies 1 without; SAVE_RAM and save-file payloads never contain the launch-owned values; other guest CMOS changes still persist.
- AC-3 Launch-disc builder: deterministic bytes (golden SHA-1 for a fixed target), recognised by `arc_media_inspect` as a 640K L descriptor with boot option 2, FileCore checksums valid, both files readable through the engine's raw reader across the side boundary.
- AC-4 Adapter wiring: with `auto` and a discovered target, the helper is published under `<save>/arcdroid/launch/<content-id>.adl` and mounted; with `off`, no helper, no overlay; option change applies at next reset.
- AC-5 `core/launch.c` boot-option fix: old-map fixtures with boot option 0–3 crossed with valid/invalid free-list pointers and full/short lengths give the documented results; E-format byte 7 read; disc names exposed.
- AC-6 Discovery on generated L, D and E fixtures (both new-directory signatures) and their JFD wrappers (D/E 1024-byte and L 256-byte sector geometries): single application → target; multiple applications with disc-name equality and trailing-digit equality → target; ambiguity → none with the candidate list; `!` directories without `!Run` → none; a candidate that cannot be inspected → `inspection incomplete`, never a target; a root with more than eight candidates is still fully inspected; non-zero boot option → none; malformed directories, out-of-range addresses, fragmented/unresolvable E objects, missing/duplicate/bad-CRC JFD sectors and illegal names → none without crash (sanitizer job covers discovery with a mutation run over the fixture family).
- AC-7 Selection safety: generated names containing `.`, `:`, `<`, `>`, `|`, `$`, `&`, `@`, `^`, `%`, `*`, `#`, `"`, space, control or top-bit characters never reach a generated file.
- AC-8 `arcdroid_launch` `app N`: selects candidate N when it is an application and overrides a non-zero boot option; N beyond the list or not an application → warning, no helper; the binding file is written on first apply and a changed resolution for the same value is refused with an OSD warning (fixture: shadow write that removes an earlier candidate).
- AC-9 Lifecycle: 100 load/unload cycles with helper generation leak nothing; playlist swaps and `.ldci` restore never regenerate the helper mid-session; a swap or eject during the first 200 frames after load neither crashes, leaks nor re-dispatches; reset after a swap re-runs discovery on the current disc.
- AC-10 Windows RetroArch CI job loads a generated option-0 application fixture with the test ROM, asserts the decision log line and the published helper file, and runs teardown as today.
- AC-11 Guards and builds: shipping-I/O, export, asset and Android ELF guards pass; host, MinGW and NDK builds pass; `ctest` passes in host and sanitizer configurations.
- AC-12 Local evidence (Fable; independently by Opus): (a) host real boot of the generated application fixture on private RISC OS 3.11 reaches the pattern with a final signature equal to the direct-boot demo disc's, and a scratch probe application shows from inside the launched task that `@` (CSD) and `&` (URD) resolve to the game disc, not the helper; a fixture whose `!Run` fails leaves a usable desktop; a swap during bootstrap yields the insert prompt or a Filer error, not another launch; (b) Odin3: Saloon Cars Deluxe disc 1 launches `!SALOON` without desktop interaction, disc 2 and Extra Courses fall back to the desktop with the OSD line, Repton 4 launches `!Repton4`, Chess 3D reaches its window; `app N` and `off` honoured after a saved per-game option; force-stop leaves no launch-owned CMOS values persisted; (c) Windows PC carried per D-024.
