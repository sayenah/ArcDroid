## Slice 10a — JFD disc writes on the native path (work order)
**Objective.** RW-flagged JFD images served by ArcDroid's own JFD reader keep the guest's disc writes across sessions, so in-game saves persist (D-073, PRD FR-43); every other JFD stays exactly as it is today. **Governing:** PRD FR-10, FR-43, FR-46, FR-50/FR-55; D-011 (eager persistence), D-014 (user content never mutated), D-019/D-029 (identity), D-028 (delta tables rejected), D-032, D-049/D-050, D-054, D-067, D-073, D-075.

**Verified repo state (`main` `7bc5132`).** `engine/arculator/src/disc_jfd.c` sets `writeprot[drive] = 1` in `jfd_load` and answers WRITE SECTOR and FORMAT with write-protect (`:60–123`); `libretro/arcdroid_libretro.c` `arc_engine_media` marks JFD media non-writable regardless of `Disk Writes` (`:2114–2118`); the JFD reader serves drive 0 only; `disc_funcs_t.writesector` (`disc.h:9`) carries neither size nor deleted-data intent; the reader selects a matching bad-ID-CRC record and reports header CRC (`disc_jfd.c` ≈`:236`); the 82C711 continuation requests DMA after `disc_writesector` unconditionally (`82c711_fdc.c` ≈`:617`) and its `getdata` can return bytes after terminal count (`:952`); launch discovery reads sectors straight from the decoded image (`core/launch_discovery.c` ≈`:169`); the existing publisher only publishes to an absent destination (`arcdroid_libretro.c` ≈`:966`) and the libretro VFS forbids renaming onto an existing file (`libretro.h`, RetroArch v1.22.2); an ADFFS package makes eligible single-disc JFDs take the ADFFS path (`arc_prepare_adffs` ≈`:2372`); `Disk Writes` changes apply at reset/re-preparation (`:5112`); eject frees the JFD (`:3292`); the parser keeps only selected descriptor flag bits (`core/jfd.c` ≈`:266`).

**Scope.** Native-path JFD sector writes (both FDCs), their persisted overlay, the effective sector view for engine and discovery, lifecycle, diagnostics, tests (host, sanitizer, Windows RetroArch), and a narrow engine interface extension. **Non-goals:** ADFFS-path or install-path saves (Slice 10b); FORMAT / WRITE TRACK; writing omitted sectors outside C-11 (reads of never-written omitted sectors keep RNF; D-067 stays for reads); JFD delta tables (D-028 stays); rewriting the user's JFD; save states; any title list, name rule or per-title profile (writability comes from the image's own header flags only).

**Constraints (D-075; Astra S28 stages 1–2 adjudicated below).**
- **C-1 Eligibility.** A JFD image is guest-writable iff its extended header's flags word has bit 1 set and bit 0 clear, it is served by ArcDroid's JFD reader (never an ADFFS carrier or an install session), and the session's effective `Disk Writes` is `Shadow` or `Original`. Legacy headers, bit 0 set, or neither bit → write-protected exactly as today. `Original` behaves as `Shadow` for JFD with one notice (as zip members, D-054). The rule applies per image in every container (bare, zip member, playlist, folder set, multi-image set, mixed-format sets) and to images inserted later through disk control; the launch helper and ADFFS carriers stay read-only.
- **C-2 Representation and identity.** A project-owned **write overlay** per decoded image, keyed by the image's own D-029 digest (SHA-1 of the decoded JFDI) under `<save>/arcdroid/jfd/` — identical decoded images share saves across packaging and machines. Records are keyed by **track-side and descriptor ordinal** (never by payload offset) and echo the base descriptor's ID, density and size. The overlay never enters any identity or digest: content identity, CMOS keys (D-019), launch binding and chooser records are unchanged, and the staged immutable JFD is never repaired from or replaced by overlay data.
- **C-3 Store format and commit protocol.** Two generation slots per image (A and B), each a complete, versioned, bounded, explicitly little-endian snapshot: magic, version, decoded length, base SHA-1 and SHA-256, generation counter, record count, then records `{track-side, ordinal, ID, density, size, data}` in strictly increasing (track-side, ordinal) order with no duplicates, then a checksum over the whole file; no trailing bytes. Bounds: records only for write-eligible descriptors (C-5), data bytes ≤ the checked sum of eligible descriptor sizes, plus an explicit global cap. **Commit per written sector, before the command completes to the guest:** write the new snapshot (generation + 1) to a bounded temporary candidate beside the slots (any stale candidate is removed first), flush, close, read it back and verify; then remove the inactive slot (it holds the superseded older generation) and rename the candidate into it. **The rename is the commit point**: only then does the new generation become the effective view and the controller report success. A process death after the rename but before the guest saw success may legitimately surface that one sector on reload. Every I/O result is checked; a missing flush callback counts as failure. **Load:** temporary candidates are never committed and are ignored (and removed on the next commit); with no slot present the image has no overlay; otherwise every present slot must be readable, valid, of a supported version, bound to this base, and the two generations must differ — then the higher generation is the effective view. **Any other state** (an unreadable, invalid, unsupported-version, mismatched or equal-generation slot) makes the image **write-protected for the session**, leaves every file byte-identical, shows the highest valid generation's view if one exists (base otherwise) and shows one OSD message saying disc writes are disabled because a saved disc-change file is damaged; ArcDroid never overwrites or deletes a committed slot in that state. The first committed generation is the first successful rename; an interrupted first write can leave only a temporary candidate. The guarantee is per-sector atomicity under process kill, not power-loss durability (a multi-sector filesystem update can stop between sectors); state that in the release note.
- **C-4 Failure.** If a commit fails before its rename (full storage, I/O, flush, close, verify, remove or rename), nothing new is committed — a fresh process loads the previous generation — the previous committed view stays effective, the command ends with a controller error (write-protect status is acceptable), every later write in the session is refused the same way, and a persistent OSD message says disc changes can no longer be saved this session. Never continue with RAM-only writes the guest believes succeeded.
- **C-5 Write contract (both controllers; shared reader).** WRITE SECTOR searches with the same rotational placement and missing-ID limits as READ (WD1770 five index pulses, 82C711 two), without resetting phase and without host latency advancing guest time. Accepted target: a payload-backed descriptor on the current track-side with matching ID and density, good ID CRC, good data CRC, not flagged slow, unique by ID and density on that track-side, and owning its payload (no other descriptor references the same payload bytes) — timed and untimed track-sides alike (timing and index behaviour unchanged). Refusals, with no mutation: omitted ID or empty track-side → Record-Not-Found (as reads); a record a read would report with header CRC → header CRC error; data-CRC-bad, slow, duplicate-ID or shared-payload records → a controller error without mutation (Sol chooses the status per controller and documents it); deleted-data writes → refused; on the 82C711 a requested N that does not equal the record's size → refused (the WD1770 derives length from the matched ID). FORMAT and WRITE TRACK stay write-protect-refused and must terminate without consuming an unbounded stream. A successful write replaces exactly that record's data; reads (and header CRC status) of that record then come from the overlay. Narrowly extend `disc_funcs_t` (or equivalent) to convey requested size and deleted-data intent; audit WD command variants so unsupported bits are not treated as ordinary writes.
- **C-6 Transfer and cleanup.** Buffer one complete sector before commit. Underrun (WD `getdata` returns -1; no byte within the controller's deadline), 82C711 early terminal count, Force Interrupt, reset, eject and media change discard the buffer and publish nothing; underrun is a bounded lost-data/overrun failure, never indefinite polling. Busy stays asserted until the commit completes; every completion or error clears DMA/DRQ and timers consistently with controller-specific result semantics. Fix the 82C711 continuation so a synchronous refusal does not request DMA. WD multi-sector writes commit sector by sector.
- **C-7 Effective view.** Engine reads, launch discovery (`core/launch_discovery.c` and anything else that reads decoded JFD sectors), reset re-preparation and disk-control insertion all see base + committed overlay; identity and digest checks use the base. The overlay is loaded and validated before discovery and lives with the mounted media entry (not machine state); controller work is cancelled before descriptors or overlay state are freed, following the existing eject ordering.
- **C-8 Lifecycle and options.** Reset and reinsert reload committed saves; unload and content switching release handles and never delete files; repeated load cycles leak nothing. `Disk Writes` changes keep today's rule (effective at reset/reload, never mid-command). Under `Off` the guest sees the pristine base read-only and the overlay stays untouched; if an overlay exists, one notice says saved disc changes are hidden while Disk Writes is Off.
- **C-9 ADFFS transition.** When a session would take the ADFFS path for an image that has a valid native overlay, it boots natively instead, logs `JFD boot: path=native reason=native-saves` and shows one notice, so a user who adds the package never silently loses saves. ADFFS carriers and the Slice 9 install path are otherwise unchanged.
- **C-10 Diagnostics.** One INFO line per prepared JFD image: `JFD writes: image=<n> state=writable|protected reason=<rw-flag|wp-flag|no-flag|legacy-header|disk-writes-off|not-native|overlay-invalid|overlay-unreadable|overlay-mismatch|layout-unsupported> generation=<g> records=<r>`; one line per committed write in the test build only; storage failures at WARN/ERROR. No OSD for normal writes.
- **C-11 Omitted-sector writes (D-076, S29; Astra S29 stage 1 PROCEED WITH CHANGES F1–F8 and stage 2 PROCEED WITH CHANGES G1–G4, all incorporated).** Write-only exception to D-067: reads of a never-written omitted sector keep Record-Not-Found.
- **C-11b Synthetic formatted sectors on writable images (D-077, Founder decision S29; Astra S29 stage 3 PROCEED WITH CHANGES, H1–H5 incorporated).** ArcDroid's own compatibility policy — not verified ADFFS semantics or recovered original formatting. When native media preparation succeeds with the image **writable** for the session (C-1 eligible, C-11 gate passed, `Disk Writes` not Off, store valid), a *virtual-sector latch* is set for that mounted lifetime: every scheduled absent P-DD5 slot of a creation-eligible, schedulable track-side is present to READ SECTOR (exactly 1024 bytes of 0x00, good ID and data CRC — the fill is fixed across reloads and versions unless explicitly migrated), READ ID and READ ADDRESS (its CHRN with good CRC at its scheduled time), using the same effective view as data reads and launch discovery; WRITE SECTOR creates it per C-11 and later reads return the written data. Captured data and errors and committed overlay data always take precedence over fill; zeros never replace an unreadable or corrupt committed record. Reads allocate no records and do not change the generation. FORMAT, WRITE TRACK and deleted-data writes stay refused; out-of-profile or irregular-track targets and gate-failed images keep RNF with the existing five/two-index limits. **Transitions:** a C-4 commit failure keeps the latch for the rest of the mounted lifetime (later writes refused; the failed target shows its previous committed data or zero fill, never the failed buffer); reset/re-preparation, reinsertion and fresh load recompute eligibility; `Off` gives pristine base reads (RNF for omitted slots); an initially damaged store gives C-3's valid committed view without virtual fill. Identity, digests, the P-DD5 inference and gate/map validation stay base-only. **Evidence:** both-controller tests for virtual reads and address sequences, wrong density, gate-failed images, aborted writes, visibility after a commit failure, damaged-store reload and `Off`→on; a test-ROM partial-sector merge (read a virtual sector, modify part, write it) preserving the untouched zero bytes, verified in a fresh process on both machine classes; Windows fresh-process read-before-write. - **C-11c Allocation-formatted blank sectors, probed-slot marks and the map-write veto (D-079, Founder S29; replaces the D-078 write-armed latch; S30, Astra stages 5–6 below).** State-based across restarts: for the same base image and committed store every mount, reset, reinsertion and fresh process starts with the same view. It amends C-11b's *activation* only; C-11b's fill (1024 × 0x00, good ID and data CRC), presentation (READ SECTOR, READ ID, READ ADDRESS at the scheduled time), precedence (captured data and errors and committed records over fill) and exclusions (FORMAT, WRITE TRACK, deleted data, out-of-profile, irregular, gate-failed, `Off`, initially damaged store) stay.
  - **Map.** The image's ADFS map is located and validated from the immutable base with the core's existing parsing (old map; new map, the one-zone P-DD5 case with its two copies). The *effective map* is the same parse over captured sectors plus committed replacement records — never over fill, never over an uncommitted buffer. With two new-map copies, each valid copy is parsed separately. No valid base map, or no valid effective copy → nothing is allocation-formatted (RNF as C-11) and no veto applies; logged once.
  - **Allocation-formatted slot.** On a writable image, an absent P-DD5 slot of a creation-eligible, schedulable track-side reads as a C-11b virtual sector iff some valid effective map copy marks at least one byte of it allocated and it carries no probe mark. This covers omissions the base map already allocates (the sports title's Save Player merge-reads track-side 116 sector 0 — allocated in its base map, never captured — before writing new space) and space the guest has since claimed. Every other absent slot keeps RNF exactly as C-11 and `main`. Derived at preparation and recomputed after every committed write; reads never change it; no per-read map parse. A freed never-written slot returns to RNF; written slots keep their records.
  - **Probe mark (session only).** On a writable image, when a guest DD READ SECTOR of a P-DD5 ID on a creation-eligible track-side 0–159, with C and H matching the physical cylinder and side, ends in RNF because that slot is absent and not allocation-formatted, the slot is marked for the mounted lifetime (cleared at reset, reinsertion, fresh load). Nothing else marks: not READ ID/ADDRESS, not Type I commands (the engine emulates no verify), not cancellation, CRC errors, density or C/H mismatches, IDs outside P-DD5. A WRITE SECTOR to a marked slot ends RNF without mutation.
  - **Map-write veto.** A guest WRITE SECTOR whose target is a map sector (as located from the base) is refused with the C-5 controller error and no mutation, before any commit step, if the effective map that write would produce (that sector replaced by the buffered data) marks any byte of a probe-marked slot allocated; the check runs per map copy on the pending buffer and publishes nothing. So a guest cannot claim space it probed as unformatted this session: title 53's protection reads track-side 158 sector 0 (RNF, marked) at every boot before its desktop is usable, and a later desktop New Directory that would allocate that sector fails cleanly at its map write instead of committing a claim that turns the next boot's probe into a blank read. One rate-limited INFO line per veto (C-10 style, `reason=probed-unformatted`).

- **Profile (F2).** The only creation profile is **P-DD5**: 80 cylinders × 2 sides (track-sides 0–159), sector IDs 0–4, size 1024 bytes (N = 3), density 2. An image *matches* P-DD5 when, among the non-empty track-sides 0–159, at least one carries the full P-DD5 set and strictly more than half are *P-DD5-compatible* (their canonical descriptor set is the full P-DD5 set or a strict subset of it, with the regular-track conditions below); one vote per track-side. Track-side slots 160–165 never vote and never gain records (captured content there stays readable as today). F-format and other layouts are out of scope until evidenced. This is a bounded inference policy, not recovered knowledge of the original disc; ADFS D and E share this physical profile and filesystem recognition is not required.
- **Creation-eligible track-side.** A track-side in 0–159 that is empty, or whose every descriptor is a distinct P-DD5 member that is payload-owning, good ID and data CRC, not slow, not ID-only, not shared (C-5 unchanged for captured replacements). Any other non-empty track-side ("irregular") never gains records.
- **Schedule (F3).** For each creation-eligible track-side the reader derives, from the immutable base only and by a versioned algorithm, one complete placement for **all** its absent P-DD5 slots at once: every captured descriptor keeps its time and relative order; created slots never collide (each sector occupies the interval from its start to start + 36 352 µs at DD — exactly the untimed packing's start-to-start spacing `(112 + 1024) × 32 µs`, with no extra gap added — and intervals of captured and created sectors never overlap, including across the index wrap); creating one sector never repositions another (captured or created). Untimed and empty track-sides: absent IDs follow the captured sequence in ascending ID order at the untimed packing spacing (a synthetic order, accepted: 5 × 36 352 µs fits one revolution). Timed track-sides: the absent IDs are placed in ascending ID order, each at the earliest start time (measured from the index, wrapping once) at or after the end of the preceding sector in that order — the preceding captured or already-scheduled sector — such that its interval overlaps no captured interval and no earlier-scheduled interval; if any absent ID cannot be placed within one revolution, the track-side is *unschedulable*. The schedule is a pure function of the base track-side: it never depends on write order or on which created records exist.
- **Image-level write gate (F1; extends C-1).** An image otherwise guest-writable by C-1 is writable only if it has **no omitted standard slot that cannot be created**: either it has no absent P-DD5 slot on any creation-eligible track-side, or it matches P-DD5 and every creation-eligible track-side (empty or regular) in 0–159 that lacks a P-DD5 slot is schedulable. Otherwise the whole image is write-protected before its first write, logged `reason=layout-unsupported` (C-10), with no OSD (it behaves as today). *Irregular* track-sides (any descriptor outside P-DD5, duplicate IDs, bad CRC, slow, ID-only or shared) never gain records. An irregular track-side in 0–159 that lacks any P-DD5 ID fails the gate **unless** the immutable base carries a valid ADFS free-space map (old map or new map, read with the core's existing map parsing and its validation) and that map marks no byte of that track-side as free (G1: the capture reproduces protection tracks faithfully, but location alone does not prove they are outside allocatable space; S29 private map check: of 7 native RW discs with such track-sides, 4 have them outside free space and stay writable — including two titles with verified overwrite saves — and 3 have free space reaching them and are protected; none of those 3 is currently playable). No runtime filesystem recognition beyond this map check. Rationale: RISC OS writes map and directory before data, so a refusal after the first write can leave a persistent partial save; the gate prevents that state for every omission ArcDroid can attribute to capture economy.
- **Command matching (F5).** Creation requires a WRITE SECTOR (not deleted-data, FORMAT, WRITE TRACK) whose C equals the physical cylinder under the head and whose H equals the selected side — the reader checks this itself for creation (it is not assumed from the existing search); 82C711 creation requires N = 3 exactly (an invalid N > 3 is refused as in M-3, never inferred); WD1770 creation takes 1024 bytes from the profile. The target ID must be an absent P-DD5 slot of a creation-eligible, schedulable track-side of a writable image.
- **Rotational semantics (F4).** During an eligible WRITE the scheduled position of each absent slot acts as a prospective target found at its next encounter within the existing search limits (WD1770 five index pulses, 82C711 two); no rotation restart, no extra index pulses, no guest time advanced by host persistence. A prospective target is invisible to READ SECTOR and READ ID/ADDRESS until the complete sector commits (C-6 transfer and cleanup rules apply unchanged). After commit a created sector joins the same rotational selection as captured ones for reads, READ ID/ADDRESS (its CHRN with good CRC) and later writes; a still-absent ID keeps RNF at the existing limits.
- **Store (F6; extends C-3).** Overlay records have two kinds: *replacement* (track-side, base ordinal; unchanged rules) and *created* (track-side, sector ID) — canonical order (track-side, kind, key), no duplicates, a created key never aliases any captured descriptor ID on that track-side. On load, created records are valid only if the immutable image matches P-DD5 and passes the static image gate, and each key is an absent slot of a creation-eligible, schedulable track-side (placement is recomputed, never read from the store); this validation is independent of session controls (`Disk Writes = Off` hides a valid overlay, it never invalidates it). Bounds: record count ≤ R + A, where R = eligible captured replacements and A = eligible absent slots (A ≤ 800 for P-DD5), bytes by the same with checked arithmetic, plus the global cap. The checksum covers kind, key, metadata and payload. A created sector's existence and payload publish together at the existing rename commit point; all memory is prepared before the rename. Damaged/unsupported/mismatched slots keep C-3 behaviour (write-protected, files untouched); development slots of the earlier format are never silently discarded or overwritten (treated as unsupported version).
- **Effective view (F7; extends C-7).** One effective-sector lookup/enumeration for captured and committed-created sectors, used by engine reads, READ ID/ADDRESS, launch discovery, reset, swap and fresh processes; base descriptor ordinals stay stable; identities and the P-DD5 inference use base bytes only.
