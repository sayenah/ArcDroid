## ADFFS probe (2026-09-21, Fable, session S18; host only; private evidence in the S18 scratchpad `adffs/`, counts and words only)
The Founder supplied ADFFS 2.88 (full and lite zips, on the dev Mac Desktop; thread `https://forums.jaspp.org.uk/forum/viewtopic.php?t=722`, not fetched — HTTP 403 is not worked around). Nothing from the package entered the repository.
- **Package facts:** requires RISC OS 3.10+; a separate 34 KB module build serves OS < 3.5 (the lite zip carries the same module and script library); needs bundled CLib 5.17, CallASWI, ZLib, BootCmds (three are third-party); loads the whole image into a dynamic area (`&D00000–&1000000` on 3.1); **no licence or redistribution statement anywhere in the package** → user-supplied only, like firmware. All ArcDroid machines have 4096 KiB.
- **ADFFS carries its own script library:** `!ADFFS.obey` is a zip of **397 boot scripts keyed by disc ID + disc number** (the `F1xxxxxNN` in the library's file names); `*ADFBootFloppy` runs the built-in script first, the JFD-embedded script only when none exists, else simulates Shift-Break. Library of 233 JFDs: 77 have both (all 77 differ; the built-in one is the maintained version — `MEMA` + `ADFCRC` guards instead of `MemoryA`, `ADFWimpSlot`, per-game `ADFJoystickKeys` pad maps in 81 of the 397), 12 built-in only, 53 embedded only, 91 neither. The 22 non-starters: 15 both, 4 embedded only, 3 neither. Built-in vocabulary is larger than S17's 21-command estimate (adds `ADFWimpSlot` 409 uses, `ADFClipScreen`, `ADFJoystickKeys`/`Mouse`, `ADFGO`, `ADFProtectModules`/`CMOS`, `ADFEmulateFDC`, `ADFInsertModule`, …).
- **Probe:** a scratch 800 K D-format disc (built with `tests/generate_fixtures.py` helpers, scratch script `mkspike.py`) holding one lone application = the minimum ADFFS files (module, the four prerequisite modules, `SetVars`, `obey`; ≈ 470 KB) + one private JFD as a file of type `&FCE`; its `!Run` copies `!ADFFS` to a 640 K RAM disc and `Filer_Run`s a second Obey file from RAM that replays ADFFS's own `!Boot`/`!Run` logic (LCD helper off, no Filer front end), then `ADFMount <file>` → `ADFS`/`NoDir`/`NoLib`/`NoURD`/`Dismount :0` → `ADFBootFloppy`. Harness: `--real-boot`, default A3000, RISC OS 3.11, 6000 fields.
- **Result (13 of the 22 fit the probe disc, ≤ ≈ 290 KB):** **10 reach their own title screen, menu or gameplay** within 30–60 s emulated (most of that is the probe's floppy-to-RAM copy); 1 is an add-on data disc that correctly asks for its game disc; 1 stopped on `ADFFS:extras.JoyMod not found` (a file the probe left out — probe limitation); 1 (no script of either kind) showed a changed screen at 60 s and an empty grey screen afterwards (undetermined). The 8 larger JFDs and the 1 ADF were not probed. **No engine or core change was needed**: ADFFS's module loads and runs on ArcDroid's ARM2/RISC OS 3.11 machine as is.
- **Platform facts established (keep):** any open file or CSD/URD/library on the floppy that ADFFS takes over produces `Please insert disc '<name>'` — the launcher must run from RAM (or another filing system), be started as a separate task (`Filer_Run`) so no Obey file stays open on ADFS, and unset the ADFS directories + `Dismount :0` after `ADFMount`; an `Echo` in a desktop-launched Obey file opens a command window that blocks until a key; `ADFFS$LCDGM Y` makes `!Run` load `3rdParty.AutoVIDC`/`LCDGameMd`.
- **Open design questions for an ADFFS path:** how the JFD (up to > 800 KB) and ≈ 470–670 KB of ADFFS files reach the guest without a hard disc (two synthesised floppies, F-format on New-IO machines only, RAM disc budget against a 4 MB machine, or a guest-visible host filing system); libretro disk control versus ADFFS's Ctrl-Shift-F1…F9 disc change and its file-name convention; write-back (`ADFFlush`/`ADFSave`) and persistence; load time; which ADFFS versions are accepted and how the package is identified (zip as supplied keeps the RISC OS file types in its `AC` extra fields); visible diagnostics for which boot path ran.

## JFD investigation (2026-09-21, Fable, session S17; host only, private evidence in the S17 scratchpad `jfd/`, counts and words only)
Founder chose the self-boot JFD investigation (PRD FR-10). All 22 self-booting titles that did not start on the Odin3 (S14 sweep: 19 black, 3 desktop; 21 JFD + 1 ADF; all present on the dev Mac under `~/Desktop/archimedes/Base Set`) were run on the host: `libretro_harness … ROMS/ROM311 <image> <dir> --real-boot`, 3000 fields (60 s), default A3000.
- **Root cause (not FDC fidelity):** a JFD carries a JASPP-authored **boot Obey script** at the end of the image (extended header +312 = length; `core/jfd.c` parses `obey_length`, nothing consumes it). ADFFS boots the title from that script instead of the disc's own `!Boot`: it sets memory (`ScreenSize`, `WimpSlot`, `RMAFree`, `SpriteFree`), loads the game files itself, applies memory patches (`MEMA`/`MemoryA`: bug fixes and removal of the original protection/auto-configure step, guarded by `ADFCRC`) and starts the code. 130 of the 233 JFD files in the library carry a script; **19 of the 21 failing JFDs** do. ArcDroid boots the disc natively, so the unpatched original loader runs and fails.
- **Host result for the 22:** 3 × ADFS `Disc error 10` (the file the native boot reads lies on a protected track whose sectors are genuinely absent from the dump — verified in the sector tables of all 3; their scripts rewrite or bypass that loader); 3 × "AutoConfiguring — Unprotect the disc and push a key" (the loader wants to write; the last FDC command is a Write Sector; the JFD reader is always write-protected; their scripts delete that step); 6 × dropped to a `*` prompt or hung after ≈ 20 FDC commands; 2 × BASIC errors (`Handle is either illegal…`, `Bad program` — the latter image uses 256-byte sectors throughout); 1 × hung at its own "Loading… please wait"; 3 × desktop (the ADF, and the only two failing JFDs that carry no script); **4 actually start** on the host (3 reach their title screen after 45–60 s, 1 waits at its own text `Y/N` prompt) — all 4 carry scripts, so **15 scripted titles fail and 3 unscripted ones sit on the desktop**.
- **Sweep classifier defect (tooling, not product):** the S13/S14 device classifier calls any frame that is > 97 % black `BLACK`, so text-mode error screens, text prompts and dark title screens were all counted as "static black screen", and the 40 s dwell is shorter than some loaders. The "16 self-booting JFDs on a black screen" figure is therefore a mix of the groups above, not one defect.
- **JFD header flags (+304) are decoded by nobody** (the core logs "unknown flags … ignored"). Public format documentation (header comment of MAME `jfd_dsk.cpp`, read for facts only, no code used): bit 0 write-protected, bit 1 read-write with deltas, bit 2 protect CMOS, bit 3 protect modules, bit 4 hide hourglass, bit 5 **requires Shift-Break**, bit 6 video-memory remap; bits 8–13 ARM compatibility (ARM3, ARM250, ARM610/710, ARM7500, StrongARM, ARMv5+); bits 16–22 RISC OS compatibility (2, 3.1, 3.5, 3.7, 4, 5, 6). In the library: 20 JFDs are **not** marked RISC OS 3.1-compatible (2 of the 22 are RISC OS 2-only; one of them starts under 3.11 anyway), 15 require Shift-Break (5 of the failing), 1 of the 22 is not marked ARM250-compatible (it starts on the A3000). `ROMS/ROM200` boots in the harness but issues 0 FDC commands with these discs (no disc boot under RISC OS 2 today; not investigated).
- **Size of the script vocabulary** (130 scripts): guards use `ADFFS$OSVersion` (89 scripts; `&31100` = 3.11) and `ADFFS$CPUID` (86; `>=&A10` = StrongARM-class, so every JIT/remap/emulate-RISC-OS branch is dead on ArcDroid's ARM2/ARM250 machines); `ADFFS$Dir` 21. ADFFS-only commands seen: `ScreenSize` 103, `GoARM3JIT` 108 (= `Go` on our machines), `ADFRemapVideoMemory` 59, `RMAFree` 49, `JITMemoryA` 43 (= `MemoryA`), `ADFEmulateRISCOS` 32, `SpriteFree` 26, `MEMA` 24, `StoreCSD`/`RestoreCSD` 21, `ADFCRC` 21, `HideCommandWindow` 15, `ADFPause` 10, `ADFForceVSync` 9, `ADFReserveMemory` 8, `GoARM4JIT` 8, `RamFSFree` 6, `ADFScreenLoad` 5, then ≈ 15 commands used by 1–3 scripts each. A set of **21 commands covers 115 of 130 scripts and 16 of the 19 scripts in the group of 22**; the scripts also rely on `<Obey$Dir>` being `@` when booted from floppy.
- **Fit with the existing design:** the core already builds a deterministic drive-1 launch disc carrying a generated Obey script (`core/launch_disc.c`); the JFD script and a compatibility layer can travel the same way. No engine FDC change is indicated by this evidence. Lemmings/Eterna direct-FDC protection (handoff S16) was not re-examined; their scripts should be read first in Slice 6a design.

## Founder decision waiting
**F-1 — how ArcDroid boots JASPP JFDs.**
- **Option A (recommended): run the image's own boot script with a project-authored compatibility layer.** For a JFD that carries a script, Launch = Auto boots the title from that script (delivered on the drive-1 launch disc) and the core supplies clean-room implementations of the ADFFS commands and `ADFFS$…` variables the scripts use (first slice: the ≈ 21-command set; unknown command → visible diagnostic, never silent). Expected gain: most of the 15 failing scripted titles, plus an unknown number of titles that today reach a screen but fail later (protected titles such as the `Disc error 10` group counted under "reach a screen"). Tradeoffs: ArcDroid executes patch scripts that ship inside the user's images, including JASPP's removal of original copy protection — the scripts are user-supplied content, ArcDroid distributes none of them and no ADFFS code, but it is a posture the Founder must accept; guest-side command support is new ARM-side or trap-based work with its own test burden; script behaviour on RISC OS 3.11/ARM2 is unverified until a prototype runs.
- **Option B: load the real ADFFS module (user-supplied, like firmware).** Highest fidelity to JASPP's tested path, but ADFFS boots image *files* from a hard disc (`ADFBootFloppy <file>`), which ArcDroid does not emulate for this purpose; redistribution terms are unverified (the JASPP site refuses automated fetches); it would make a third-party closed module a runtime dependency. Not recommended.
- **Option C: FDC/media-fidelity work only.** Does not fix this group: the dumps do not contain the protected sectors and the write step cannot succeed on a protected image. Not recommended as the next slice.
- **S18 revision (after the ADFFS probe):** Option B's main objections fell — it runs on RISC OS 3.11/ARM2 unchanged, needs no hard disc (RAM disc worked) and booted 10 of 13 probed non-starters with JASPP's maintained scripts; redistribution stays impossible (no licence text), so B means **user-supplied ADFFS, identified and loaded like firmware**; without it the title boots natively as today, with a visible notice. Option A's remaining value is zero-setup coverage for users without ADFFS (130 of 233 JFDs carry an embedded, older script) at the cost of a ≈ 30-command clean-room layer; Fable now recommends **B first, A recorded as a follow-on candidate decided on demand**. The Founder asked in S18 about doing both and then "why bother with A"; no final answer yet. The posture question is unchanged for either option: ArcDroid would execute JASPP patch scripts (including removal of original protection) that the user supplies.
- Secondary questions the Founder may answer now or at Slice 6a review: (1) should Auto honour the JFD flags — Shift-Break boot, RISC OS/ARM compatibility warnings, machine choice? (2) should a JFD marked read-write get an in-memory (non-persistent) or persisted write overlay for titles that save to their disc?
